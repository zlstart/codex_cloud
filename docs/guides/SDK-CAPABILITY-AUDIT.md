# Python Agents SDK reuse audit (0.24.0)

Audit completed against SDK **0.24.0**, starting from commit `3998b92`. Official docs and installed source were checked before implementing agent capabilities. Dependencies are locked; upgrades must repeat native sandbox/protocol checks. Actual validation is recorded in [the SDK verification report](../reports/2026-11-02/sdk-native/README.md).

| Area | Existing implementation | Selected SDK primitive / application boundary |
|---|---|---|
| Model loop | Runner plus bespoke tool wrappers | Runner + SandboxAgent, OpenAIResponsesModel only |
| Shell/Python | Custom Docker command runner | Shell capability: exec_command/write_stdin; Python through native shell |
| File manipulation/images | Custom read/write/image functions | Filesystem capability: apply_patch/view_image; native shell for reading/search |
| Docker isolation | Custom per-command container | DockerSandboxClient lifecycle with narrow trusted creation-policy adapter for missing resource options/root bind |
| Skills | Custom catalog/list_skills/load_skill | Skills with native Skill entries, catalog and on-demand reads of SDK-materialized files; removed custom loaders |
| MCP | MCPServerStreamableHttp | Retain SDK transport and native approval; application owns allowed endpoints/secrets/CRUD |
| Conversation | Reconstructed text-only bounded_history | SQLiteSession outside model workspace; full item persistence and one-time legacy seed |
| Context | Character truncation | Native Compaction + ToolOutputTrimmer; provider compatibility explicit |
| Delegation | Missing | Agent.as_tool + nested streaming; independently configured specialists |
| Plan/Todo | update_plan | Keep small product-specific function; no general SDK todo tool found |
| Approvals | SDK interruptions + app records | Retain SDK RunState flow, application authorizes each decision |
| Streaming | Concatenated text + separate tools | SDK events mapped to ordered durable product events with call/item identities |
| OpenAI Traces | Tracing unconditionally disabled | SDK trace() scope + RunConfig tracing policy + native BatchTraceProcessor/BackendSpanExporter and process-exit flush; app owns explicit opt-in, separate tracing credential and authorized link/status event |
| Files/UI/auth | Application-specific | Keep authorization, preview delivery, rendering and capability editors in application |

Implementation and verification notes:

- The empty-installation model default is aligned with SDK 0.24: `gpt-5.6-luna`. Existing administrator/environment model choices retain precedence.

- Native `Filesystem`, `Shell`, `Skills`, `DockerSandboxClient` exercised in real Docker. Python execution now uses native `exec_command`; no custom tool loop or host-execution fallback remains.
- Docker SDK options omit root bind/resource controls. `PolicyContainers.create` adds trusted per-chat mount, read-only uploads/root, nonroot UID/GID, resource limits and executable `/tmp`; the SDK owns exec/PTY/patch/image/lifecycle. Network access is enabled and verified with HTTPS. Application quota monitoring remains necessary.
- SDK 0.24 Docker async lifecycle methods contain synchronous docker-py I/O. `runtime_worker` owns the entire native run in a dedicated worker event loop so slow daemon calls do not block other users' API/SSE requests. Events and approval callbacks bridge to the API loop; cancellation joins native cleanup and thread shutdown. SDK session locks remain on one loop.
- `SQLiteSession` owns complete model history. Each chat has a separate database under `DATA_DIR/history`, outside the sandbox. Existing UI transcripts seed an empty SDK history only once.
- Sandbox `Compaction` and local `ToolOutputTrimmer` are separate operations. The trimmer shortens old tool output; it is not semantic summarization. SDK compaction request/returned-item handling and shortened subsequent context pass protocol tests. Current DashScope `glm-5.3` accepted parameters but returned no compaction item in two live probes; do not claim live compaction support for that provider.
- The alternate `OpenAIResponsesCompactionSession` uses `/responses/compact` and SDK 0.24.0 restricts accepted model names; it is not a transparent fallback for arbitrary third-party Responses models. No silent fallback is installed.
- Compaction regression audit (2026-11-04, SDK 0.24.0): a new real-SDK/HTTP-fixture test reproduced a same-run gap: sandbox preparation processes the original run input, while `run_internal/run_loop.py` subsequently appends generated model/tool items. A compaction emitted during that run therefore did not remove the earlier tool turns from the next model request. The application now composes the documented `RunConfig.call_model_input_filter` with native `ToolOutputTrimmer` and `Compaction.process_context` on the complete request. This uses the SDK's latest-compaction boundary, preserves instructions and complete post-boundary tool pairs, leaves durable SQLite history intact, and never creates a summary or drops history without a returned compaction item. Sources checked before implementation: official [compaction capability](https://openai.github.io/openai-agents-python/ref/sandbox/capabilities/compaction/), [RunConfig/input filter](https://openai.github.io/openai-agents-python/ref/run/), [ToolOutputTrimmer](https://openai.github.io/openai-agents-python/ref/extensions/tool_output_trimmer/) and [Responses compaction guide](https://developers.openai.com/api/docs/guides/compaction); installed `sandbox/capabilities/compaction.py`, `sandbox/runtime_agent_preparation.py`, `sandbox/runtime.py`, `run_internal/run_loop.py`, `run_config.py`, and `extensions/tool_output_trimmer.py`.
- Compaction observability now consumes public `RawResponsesStreamEvent` → `response.completed`: `context.status` records only scoped response identity, configured threshold, provider-reported input tokens, actual compaction-item count and one of `compacted`, `threshold_exceeded`, or `not_observed`. Crossing the reported-input threshold without an item is an observation, not a claim that the provider is categorically unsupported; reported usage is not guaranteed to equal the provider's internal rendered-context counter. Missing usage remains unknown. Existing `context.compacted` deduplication and encrypted-content exclusion remain intact.
- Live retest (2026-11-04) used the environment's current **DashScope `qwen3.8-flash`**, not the historical `glm-5.3`: four real streaming Responses calls accepted thresholds 1,024 / 32,000, with input-token counts 6,526 / 6,405 / 41,296 / 41,167, and returned **zero compaction items**. A separate real-Docker application run and reopened-session follow-up reported 10,775 / 11,063 / 11,171 input tokens at threshold 1,024, correctly emitted `threshold_exceeded`, preserved an early project fact and a later correction, and completed a native `exec_command` round trip. These prove ordinary continuation and honest status reporting, not live compressed-memory retention. Deterministic protocol tests separately cover actual compaction-item consumption, same-run post-compaction tool pairs, latest-window reuse after SQLite reopen, repeated compaction, and recovery after provider failure. Evidence is recorded in the task's `/workspace/qa-artifacts/compaction/`; no production model/protocol change or synthetic compaction fallback was made.
- Subagents use `Agent.as_tool`, separate model histories and selected Skills/MCP, sharing only the authorized chat sandbox. Same-agent concurrent reuse is rejected by SDK; `ToolExecutionConfig(max_function_tool_concurrency=1)` serializes shared-workspace calls. Native child custom patch/exec and artifact delivery passed a live provider run.
- Native SDK interruptions/`RunState` handle MCP approval and resumption, including nested child approval. Product records enforce user ownership; regression checks ensure one execution and no duplicate input on resume.
- `RawResponsesStreamEvent`, `RunItemStreamEvent`, `ResponseOutputMessage` and nested `AgentToolStreamEvent` map to one durable timeline with scoped item/call IDs. Raw+run-item duplicates are reconciled; reasoning/encrypted compaction payloads are not exposed in browser events. Live/replay share one frontend reducer.
- Tool display consumes the public `ToolCallOutputItem.raw_item` and its documented `custom_data`. Native shell stdout/stderr/outcome and explicit failure states remain visible, bounded text includes a truncation notice, and file outputs retain only names/IDs rather than inline bytes. `MCPServerStreamableHttp(custom_data_extractor=...)` maps the SDK's `MCPToolCustomDataContext.is_error` to one application status field; private MCP metadata is not forwarded. Checked against the official [items reference](https://openai.github.io/openai-agents-python/ref/items/), [MCP reference](https://openai.github.io/openai-agents-python/ref/mcp/server/) and installed SDK 0.24 `items.py`, `mcp/server.py`, `mcp/util.py`.
- OpenAI Traces integration was checked against the official tracing guide and installed SDK 0.24.0 `tracing/create.py`, `tracing/provider.py`, `tracing/processors.py`, `tracing/setup.py`, `run_config.py` and `models/openai_responses.py`. One outer `trace()` spans approval resumption and delegated runners; the conversation groups separate run traces. Per-trace `tracing={"api_key": ...}` keeps the dedicated OpenAI credential independent of the third-party Responses client. Native sensitive-data capture is explicitly false unless opted in. Native background batching and bounded process-exit shutdown own delivery; synchronous `flush_traces()` is intentionally omitted at each run end because its unbounded network wait would delay results/cancellation. The owner-authorized `run.tracing` event exposes configuration status and dashboard link, not a delivery acknowledgement. See [configuration and privacy details](TRACING.md).
- SDK 0.24 `ResponseSpanData.export()` sends correlation ID/usage rather than full model input/output; the OpenAI dashboard cannot retrieve a third-party provider's Responses result. Sensitive capture remains opt-in for native model data retained by processors and for exported function-tool arguments/output; the app does not invent a custom ingestion payload to copy third-party model content.
- `update_plan` is the remaining product-specific agent tool. Auth, capability CRUD, secure artifact delivery, Office parsing and frontend rendering have no corresponding general SDK product implementation.
- Production acceptance exposed a third-party Responses call omitting `update_plan.completed`. The SDK `function_tool` / generated Pydantic model now applies a safe `False` default while retaining strict schema generation. Its documented `failure_error_function` returns a fixed actionable JSON error instead of the generic retry text; invalid plans never emit UI updates. Checked official [function-tool error handling](https://openai.github.io/openai-agents-python/tools/#handling-errors-in-function-tools), SDK 0.24 `tool.py` argument validation and `function_schema.py`. Real complex HTML generation exceeded the original 300-second application deadline; the bounded default is now 900 seconds, with cancellation and Docker resource limits unchanged.

Official sources:

- A live five-format report run emitted the nonexistent `write_file` function and failed with `ModelBehaviorError`. The documented `RunConfig.tool_not_found_behavior="return_error_to_model"` now returns an SDK-owned error result and permits correction; `tool_error_formatter` supplies a fixed JSON error for clear UI status. No unknown tool is executed or mapped to a host operation. Verified with official [RunConfig reference](https://openai.github.io/openai-agents-python/ref/run/#agents.run.RunConfig.tool_not_found_behavior), installed `run_config.py` and native deterministic Responses round trips (unknown tool → valid plan tool → final answer).

- Production Snake acceptance also reached the native `MaxTurnsExceeded` boundary after 20 model turns while creating and self-checking a real file. `Runner.run_streamed(max_turns=...)` remains the enforcement primitive; the application default is now 40 turns, still bounded by the 900-second deadline. Failed attempts retain files and full native session history so a user can continue without regenerating their work.

- Docker startup acceptance (2026-11-03): SDK `DockerSandboxClient` remains the lifecycle primitive; its injected docker-py client uses the library's 60-second default instead of an application-imposed 15 seconds. The managed vfs daemon reproducibly needed 22.281 seconds for `POST /containers/create`; three 15-second attempts failed before any model call. `FAMSUN_DOCKER_TIMEOUT_SECONDS` permits 1–300 seconds. The application creation-policy adapter adds a unique name/attempt label solely to reconcile ambiguous create responses that leave the SDK without a container object. Reconciliation never removes another attempt, is bounded, and reports unconfirmed cleanup honestly. Safe `SandboxError` messages distinguish Docker startup failures from provider errors. Sources: [SDK Docker reference](https://openai.github.io/openai-agents-python/ref/sandbox/sandboxes/docker/), installed `agents/sandbox/sandboxes/docker.py` (`create`, `_create_container`, `_cleanup_failed_create_resources`), and docker-py `models/containers.py` (`create`). Evidence is in `test-results/production-acceptance-2026-11-03/docker-startup-diagnostic.json` and `docker-startup-60s-diagnostic.json`.

- Tool outcome acceptance (2026-11-04): actual Qwen Responses custom `apply_patch` calls with malformed patch envelopes returned an error string but no failure status. SDK 0.24 `CustomToolAction` catches exceptions independently of `RunConfig.tool_error_formatter`. The public `Filesystem.configure_tools` hook observes only the native invocation exception and re-raises it unchanged; `CustomTool.custom_data_extractor` transfers a per-call `famsun_tool_status=failed` flag to the existing timeline adapter. Native patch execution, grammar, path checks, output, approvals and recovery remain SDK-owned. No error is inferred from arbitrary output text. Sources: [Filesystem configurator](https://openai.github.io/openai-agents-python/ref/sandbox/capabilities/filesystem/), [custom tool metadata](https://openai.github.io/openai-agents-python/ref/tool/#agents.tool.CustomTool), installed `agents/run_internal/tool_actions.py` and `agents/sandbox/capabilities/filesystem.py`. Regression `tests/test_patch_tool_status.py` reproduces the missing status before the fix and verifies native patch recovery afterward.
- Sandbox dependency acceptance (2026-11-04): a real factory-report run used the standard `file` command to inspect inputs and exited 127 because the image omitted it. Added the Debian `file` package and a native Docker smoke assertion; execution remains the SDK Shell capability in the isolated container. Before/after command and image rebuild evidence is in the external QA evidence bundle.
- Shell acceptance also found `time` missing and a `... | tail` pipeline returning zero after its first command failed. Added `time` to the sandbox and documented the SDK shell parameter: POSIX sh by default, explicit `/bin/bash` for Bash syntax, and `set -o pipefail` for pipelines. The Docker smoke verifies an upstream exit 7 remains 7 under Bash pipefail. This keeps native Shell behavior; arbitrary stderr text is not reclassified as a failed command.
